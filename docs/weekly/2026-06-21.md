## TL;DR

The feature well is now dry. I ran the last batch of feature experiments and
only one paid off — adding each inspection's own outcome lifted us ~+0.05 PR-AUC
on both models (the contract is now at v36). Everything else came back flat:
two more passes at 311 data, deeper inspection history, and both deep-learning
spikes on the violation comment text. The headline is that we've hit an
**information ceiling, not a model ceiling** — XGBoost and LogReg are now
basically tied, so chasing fancier models won't help. On the app side I built
explainability end to end (driver bars, calibrated waterfall, drivers on the
map and list), reshipped scores.json at schema 0.4.0, and stood up a CI test
gate that runs on every push to main.

## What changed

### Modeling

- **The one keeper — current-inspection outcome features (PR #15).** Each
  anchor inspection's own outcome — `was_fail`, priority count, core count —
  was already computed inside the pipeline and thrown away at the return. I
  promoted the three columns (leak-free: observed at `as_of_date`, label window
  strictly after). Biggest lift of any experiment: served LogReg PR-AUC
  0.291 → 0.344, precision@10% 0.326 → 0.369; XGBoost moved the same amount.
  **Contract is now v36.** Caveat documented: the top decile is ~91% recent
  failers (a Fail triggers a mandated re-inspection that lands in the window),
  so the UI must show "recently failed." Gain persists on never-failed and
  cold-start rows, so it's real forward signal, not only the re-inspection
  artifact.
- **Flat, dropped (PR #20):**
  - **311 redesign** — re-attacked the flat radius counts two new ways:
    address-exact venue matching and a neighborhood-normalized excess (ring
    probe). Strong univariate separation, but redundant with `prior_*`
    inspection history at every spatial scale. Fails the both-metrics gate.
  - **Inspection-history depth** — historical hazard-type keyword counts +
    chronic/repeat-violation features. One morsel looked positive on a single
    split; **expanding-window CV killed it** (a lucky 2020 window). History is
    already well summarized by the existing `prior_*` features.
- **Deep-learning spikes on the violation comment text — both null:**
  - **Embeddings (PR #28):** Titan Text Embeddings V2 → PCA(32) → both models.
    Flat / slightly down on the production LogReg.
  - **LLM structured labels (PR #35):** Nova Lite (forced tool-use) extracted
    hazard type / severity / imminent / corrected-on-site over 90k distinct
    comments. Same null verdict.
  - Takeaway: the free text is **redundant with codes 1–29 + the 12 keyword
    flags**, not under-encoded. Code kept in-tree but unwired.
- **Core-code / allergen break-out ablation (PR #33) — null.** Core codes are
  not uniform (1.2×–2.4× lift), and the raw data has ~20k allergen mentions
  (code 58), but breaking them out fails the both-metrics gate. The generic
  `n_core` rollup already captures it. Allergen is a product angle, not a
  modeling lever.

### Label decision (PR #22, decision record 0007)

- Tested narrowing the target to **fail-only**. With proper expanding-window CV
  it *is* more learnable (mean PR-lift 3.61 vs 3.22, 6/6 folds). **But I kept
  the broader `fail-or-priority` label** on product grounds: codes 1–29 are
  Chicago's own priority-hazard tier, we already use that classification in the
  label, ~8 features, and the UI. Fail-only would narrow us to a
  "regulatory-failure" predictor and cut hazard recall for vulnerable groups
  (daycares, schools, hospitals). Recorded as decision record 0007 + an ethics
  principle in 0005.
- **Missingness indicator** quick-win (`SimpleImputer(add_indicator=True)`) —
  flat, dropped. The indicators are redundant with `prior_inspections` /
  `prior_fails`, which already encode no-prior-history.

### Fairness + scope (PR #23)

- **Scope correction:** the data covers **all licensed food establishments
  (~69% restaurants)**, not just restaurants. Recorded a Scope section in the
  interface contracts + CLAUDE.md, and swept user-facing copy to "food
  establishment" (PR #19).
- **Reusable fairness audit** — `evaluate.group_performance_audit()` (per-group
  n / prevalence / PR-AUC / precision@10 / recall@10 + below-floor flag), so
  every new experiment runs the same check. No evidence of systematic
  unfairness on coverage; the full disparate-impact (census) audit stays Phase 2.
- **`facility_type` normalization** (audit/UI only) — collapses the ~500-value
  free-text tail into canonical buckets (senior daycare separated from child
  daycare, etc.).

### App / explainability

- **Detail-page explainability (PR #19):** diverging driver bars (raises vs
  lowers from a centre axis), a top-factor chip, gauge bug fixes, and a
  full-width score-card band. WCAG AA contrast fixes throughout.
- **Drivers on the map and list (PR #27):** each establishment's top risk
  driver now shows on map pins and list rows (no schema change — derived from
  the existing `top_drivers`).
- **Methodology page (PR #31):** global feature-impact chart (mean |log-odds|)
  + one worked, calibration-faithful waterfall; home page gained an example-
  drivers card relevant to immunocompromised diners.
- **Serve reship (PR #32):** scores.json schema **0.3.0 → 0.4.0** — `top_drivers`
  4 → 5 + a top-level `calibration {a,b,intercept}` triple shipped once. The
  detail page reconstructs each establishment's calibrated waterfall
  client-side, so there's no per-row payload cost. Deterministic retrain ⇒
  **zero score/tier shift**.
- **Search UX (PR #29):** server-side search / sort / filter driven by URL
  params; reaches every tier + the ~0.5% coordless rows, with an honest
  "Top N by risk" default and A–Z browse. Fixed a debounce race that dropped
  typed queries. Also fixed mobile horizontal overflow across the detail and
  methodology pages.

## Open items / next up

- **The feature well is dry.** Five-plus flat experiments + both DL nulls + XGB
  pulling even all point to an **information ceiling, not a model ceiling**.
  Future gains are not more features or models. The real levers are:
  - **Deconfound the label** — inspection-arrival / exposure bias and the
    unobserved inspector-strictness effect (inspector identity is missing from
    the Chicago feed entirely).
  - **Orthogonal external data** — building permits, NOAA weather,
    chain-vs-independent. Avoid cuisine / inspector-as-feature / Yelp (fairness
    and legal traps; Yelp has no open Chicago data).
- **Production-estimator revisit (decision record 0009):** under v36, XGBoost
  and LogReg are tied — the old "LogReg wins the operating points" basis no
  longer holds cleanly. Served LogReg is still production; needs a decision.
- **Agent-into-app integration is Phase 2.** The chatbot stub (PR #21) is
  closed, not merged — the data flow is currently backwards and the real path
  needs a design conversation.
- **Census disparate-impact audit** stays Phase 2 (the real fairness gate).

## One learning

A feature that looks positive on one chronological split can be a lucky window.
Run 3's repeat-violation morsel showed +0.0072 on the 2020 fold and looked like
a keeper; expanding-window CV averaged it out to roughly zero. When a candidate
is a marginal adopt — small effect, real blast radius — CV is what tells a true
signal apart from a single-split false positive.
