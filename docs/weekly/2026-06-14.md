## What changed

### Modeling
- **4 new leak-safe features (26 → 30 contract):** `static_inspection_type`,
  `prior_pass_w_conditions`, `prior_reinspections`, `prior_complaint_inspections`.
  Served (logreg + sigmoid, RT-filtered): **PR-AUC 0.299 → 0.315,
  precision@10% 0.338 → 0.352**.
- **XGBoost validation fix:** early stopping was watching the same validation
  set we scored on (a double-dip). It now early-stops on an embargoed tail of
  train, refits on full train at the fixed tree count, and validation is used
  only for calibration. Honest test (unfiltered, n=13,812): **PR-AUC
  0.254 → 0.268, log-loss 0.282 → 0.261**.
- **Production estimator:** XGBoost clears PR-AUC but misses precision@10%, so
  by our both-metrics gate the **logistic-regression baseline stays in
  production**.
- **Features tested and left out (flat):**
  - 311 spatial counts (PR-AUC 0.3147 → 0.3152)
  - operator / license-history features (0.3147 → 0.3151)
  - per-violation-type counts (codes 1–29): XGB 0.2681 → 0.2687, LogReg
    0.2660 → 0.2663 — the codes are already saturated by the priority/core
    rollups and keyword flags.
  - violation comment-text severity (`prior_serious_mentions`,
    `prior_corrected_rate`, `prior_distinct_violations_mean`): flat on the
    served LogReg (PR-AUC 0.3147 → 0.3128) and *negative* on XGBoost
    (0.2681 → 0.2613, lift 3.37 → 3.21). The features get real weights but are
    collinear with the existing `prior_*` counts, so they split the same signal
    without adding any.
  - Layer C TF-IDF → SVD(50) embedding of the violation text (prior-mean,
    leak-free): flat on both — LogReg PR-AUC 0.3147 → 0.3138 (precision@10%
    0.352 → 0.341, the 50 dims add noise), XGB 0.2681 → 0.2676. Fifth angle on
    the same text to come up empty; implemented as the "we did NLP" deliverable.

  Please don't re-try these without new data — the existing `prior_*` history
  already captures the signal. (Also found: `license_status` is uniformly `AAI`
  everywhere, so there's no revoke/closed signal to mine; `account_number` only
  exists in the current-license file.)

- **Declined on fairness grounds (not tested):** neighborhood peer-fail-rate
  (prior fail-rate of *other* nearby restaurants). In segregated Chicago this is
  a geographic proxy for race / income, it punishes a clean restaurant for its
  neighbors' behavior (individual unfairness), and it risks a predictive-policing
  feedback loop (flag an area → inspect it more → find more → "confirm" the flag).
  The product is consumer-facing, so the harm would concentrate on disadvantaged
  neighborhoods. Expected gain is low anyway (311 spatial counts were flat).
  Revisit only behind a disparate-impact audit (Phase 2).
- **Fairness watch on features we already ship:** `static_zip` (and, to a lesser
  degree, `static_facility_type` — our single strongest feature) are geographic /
  business-type signals that can proxy for demographics. The in-scope group-perf
  check by `facility_type` + zip-prefix must be run and reported; if `static_zip`
  drives disparate impact without much accuracy, consider coarsening or dropping it.

### Fairness audit + feature refresh (this session)
- **Ran the in-scope group-performance audit** on the served model:
  - `static_zip`: well-calibrated on average but real per-zip miscalibration —
    over-flags some low-risk areas (incl. Pilsen / Chinatown zips), under-flags
    high-risk downtown. Full disparate-impact-by-protected-class needs a census
    join (Phase 2).
  - `static_facility_type`: mild over-prediction in low-risk types; ablation
    shows it adds ~no accuracy (PR-AUC 0.3147 → 0.3139).
  - `prior_*` exposure bias: `prior_fails` is largely driven by inspection
    FREQUENCY (corr 0.79), which is unequal by group and barely predicts true
    risk (corr 0.05). Validity caveat — consider rate-normalization (Phase 2).
- **Acted on it — dropped `static_zip` + `static_facility_type`.** `static_zip`
  is a geographic proxy; `static_facility_type` only *partly* correlates with
  immigrant/ethnic business types and its real risk signal is largely redundant
  with the kept `static_risk_tier` — so both drop ~free. The ablation showed
  dropping `static_zip` actually *improves* the model (its sparse high-cardinality
  dummies overfit the chronological split). Win-win: better accuracy AND less bias.
- **Feature-refresh PR (stacked on #9):** added 5 leak-free OWN-HISTORY recency /
  trend features (`last_was_fail`, `prev_priority_violations`,
  `priority_violation_trend`, `prior_fails_365d`, `prior_priority_violations_365d`)
  and dropped the two proxies. Net served **PR-AUC 0.3147 → 0.3246, precision@10%
  0.352 → 0.364, recall@10% 0.327 → 0.337**; XGB PR-AUC 0.2681 → 0.2882. Both
  metrics up on both models. **30 → 33 feature contract → needs owner acks.**

### Evaluation
- **Added recall@k** (top 5/10/20%) to the eval suite — every run now logs it.
  Served **recall@10% ≈ 0.33** (we catch about a third of real risks in the top
  decile). This adds new fields to every `reports/metrics/*.json`.
- **Time-based cross-validation** (`expanding_year_folds`, full-year, 180-day
  embargo) + 5 leakage-guard tests. Config is stable: PR-AUC 0.326 ± 0.029
  across 2020–2024. Sigmoid chosen over isotonic by mean Brier across folds.

## One learning

If early stopping watches the same validation set you later score on, you're
tuning on your test data — the reported metric looks better than it really is.
The fix was to early-stop on an embargoed tail of train and reserve validation
for calibration only.
