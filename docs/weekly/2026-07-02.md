## 1. BUG (live in prod): the chat agent reports "stable" trend for every venue

**Owners: Bella (eval / serve / scores contract) + Deepak (agents).**

Decision [0011](../decisions/0011-trend-signal-forecast-model-last-k-visits.md)
renamed `trend_slope_90d` → `trend_slope` (schema 0.4.0 → 0.5.0). The pipeline
(#61), the web app (#62), the contract doc, and the published S3 `scores.json`
(regenerated 2026-06-29 09:35 UTC) all shipped the rename. The **agent tool
handlers did not**:

- `agents/tools/get_safety_score/handler.py:385` and
  `agents/tools/explain_restaurant/handler.py:120-121` still read
  `record.get("trend_slope_90d")` — always `None` against the 0.5.0 file.
- `_trend_label(None)` returns **"stable"**, not "unknown"
  (`get_safety_score/handler.py:443-445`).
- The runtime downloads `scores.json` from S3 on cold start
  (`agents/entrypoint.py:8`), so every deployed agent answer since June 29
  reports trend "stable" — a confidently wrong answer, not a missing one.

**Verified repro** (actual handler code against the actual live S3 file):
CAPT'N NEMOS, 3650 N Ashland Ave has `trend_slope = +0.0124` — one of the
fastest-**worsening** High-tier venues in the city. Tool output:

```json
{"risk_tier": "High", "trend": "stable", "status": "scored"}
```

**Why every safety net missed it:**

1. `.get()` is silent — a missing key looks like a legitimately-null slope.
2. Local dev masks it: `agents/run_local.py` defaults to the **committed**
   `app/public/data/scores.json`, which is still 0.4.0 with `trend_slope_90d`
   present — the agent works perfectly locally, only the deployed one breaks.
3. The handler unit-test fixtures hand-build records with the old field name
   (`get_safety_score/test_handler.py:159-183`), so tests pass against a shape
   production no longer serves.
4. The eval faithfulness gate checks score/tier but never trend (zero "trend"
   mentions in `agents/eval/run_eval.py`), so the June-29 agent deploys passed
   their post-deploy gates.

**Fix checklist** (small — the handler part is ~3 lines + fixtures):

- [ ] Rename the field reads in both handlers + their test fixtures
- [ ] Decide `_trend_label(None)` semantics — "stable" vs "unknown". Under
      0.5.0, null means "<2 scored visits"; reporting that as "stable" is what
      made this silent. Product/responsible-AI call (decision 0005 framing) —
      Bella's call, please don't let the fix PR decide it by default.
- [ ] Regenerate the committed `app/public/data/scores.json` fallback on 0.5.0
      (restores local-dev parity)
- [ ] Add trend to the eval's deterministic faithfulness gate — the regression
      net that would have caught this class of bug
- [ ] Flip 0011's status from "Proposed" and note the agent-side completion
- [ ] Cosmetic: stale name in `scripts/run_trend_deconfound_experiment.py:3`

Merging the handler fix auto-deploys via `deploy-agent.yml` and is gated by the
post-deploy scoring smoke test.

**Process note (PM hat):** 0011 planned a stacked delivery (pipeline PR, app PR,
follow-up) but no owner per piece and no implementation-status field — the
pipeline and app halves shipped while the record still said "Proposed", so
nothing looked unfinished. Proposal: decision records with contract changes get
a one-line implementation checklist, and a schema rename greps the repo for the
old name before the deprecating PR merges.
