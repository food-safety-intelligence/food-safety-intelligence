## TL;DR

This was the week Phase 2 actually went to production. Four big shifts:

1. **The production model is now XGBoost.** A depth-3 monotone XGBoost beat the
   served LogReg baseline on a corrected, like-for-like test, so it was promoted
   (#52). The same review found the "building-violation features" gain from #44
   was a measurement artifact and reverted those features.
2. **The chat agent grew up.** It went from a stub to a responsible, evaluated,
   single canonical runtime: anti-fabrication guardrails, a no-record rule (never
   invent a score), name-based matching, third-party review links, multi-turn
   memory, an eval harness, and per-request isolation (#55–#60, #63, #65, #66,
   #70, #72, #74, #75, #80).
3. **Deploy was rebuilt on AWS.** The pipeline IO now runs local-or-S3 through one
   seam (#64, re-landing the stranded #40); the web app deploys to CloudFront/S3
   on every push to `main` (#67) and the agent auto-deploys too (#82). Amplify/Vercel
   are retired.
4. **The trend signal was fixed.** The broken `trend_slope_90d` is replaced by a
   forward-looking `trend_slope` from a forecast-only model over the last 5 visits,
   with a real per-inspection chart (#61 backend, #62 frontend; schema 0.5.0).

Two cross-team contract changes landed: **production estimator LogReg → XGBoost**,
and **`scores.json` `trend_slope_90d` → `trend_slope` (schema 0.4.0 → 0.5.0)**.

## Modeling

### Production estimator promoted to XGBoost (#52, Bella)

This started as a review of #44 and turned into a model update.

- **The #44 gain was a measurement artifact.** #44 reported the 9 building-violation
  features gave XGBoost +0.0198 PR-AUC / +0.0231 precision@10%. That compared a
  fresh candidate against a **stale stored control computed on a different test
  set** (8.85% base rate vs 10.5%). PR-AUC and precision scale with the base rate,
  so the "gain" was manufactured by the base-rate difference. The tell: ROC-AUC and
  top-decile lift — which don't move with base rate — both went *down*. Re-run
  honestly (same rows, both arms, all model families), the building features are
  flat-to-negative and were **reverted** from `ALL_FEATURES` (the feature module is
  kept in-tree, unwired).
- **Depth-3 monotone XGBoost wins.** On the correct test (n=7,008, base 10.8%) a
  depth-3 XGBoost with monotone constraints on the risk-count features beats the
  served LogReg: **PR-AUC 0.382 vs 0.372**, precision@10% ties. Under expanding-window
  cross-validation it wins **both** metrics in **5/6 folds**. (The old depth-6 default
  lost because deep trees can't extrapolate the forward-time `prior_*` counts;
  depth-3 + monotone fixes the top decile.)
- **Explainability** is solved with XGBoost **native TreeSHAP** — no new `shap`
  dependency, and the `scores.json` schema + waterfall are unchanged. Served via
  `scripts/retrain_xgb_sigmoid.py`. This closes decision record 0009.

### Building-violation features (#44, Deepak) — added, then reverted

#44 added 9 block-face building-violation features plus a standalone fetch script
(`fetch_building_violations.py`) and the full `build_features.py` pipeline. The
features themselves were reverted by #52 (see above), but the **pipeline scripts
stayed** and are now part of the standard build.

### Deep-learning MLP benchmark (#47, Aurelia)

Added an MLP benchmark notebook (nb07). Properly seed-averaged and sigmoid-calibrated,
the MLP only **ties** LogReg (~0.371) — it is kept as a benchmark, not served. (#48
was an empty placeholder branch.) #52 later corrected nb07 to evaluate on the right
test set (it had been scoring on the deflated right-truncation-kept set).

### Forward-looking trend signal (#61 backend, Bella) — decision record 0011

The shipped `trend_slope_90d` was broken two ways: null for ~70% of establishments
(it needs 2 inspections inside a 90-day window) and, when present, it tracked the
mandated fail → re-inspection swing rather than real drift. The fix turns two knobs:

- **Window:** 90 days → **last 5 visits** (coverage 0.29 → ~0.87).
- **Score basis:** production model → a new **forecast-only "Model 2"** that drops
  the 3 current-outcome features, so the trend doesn't see today's verdict.

The production `risk_score` is **unchanged**. The new `trend_slope` is shipped as an
**additive descriptive trend + early-warning watch-list**, not a predictive
improving/worsening/stable verdict (a strict steeply-rising watch-list lifts 2.26×,
but a loose "is it rising" signal is uninformative at ~1.16×). `predict_batch` now
emits `trend_slope`, the field is renamed in `scores.json` (**schema 0.4.0 → 0.5.0**),
and per-inspection forecast scores are written to `forecast_history.parquet` for the
chart.

### Experiment-log note

The model-experiments log now also records the full 2026-06-27 building-violation
re-evaluation and the 2026-06-28 forward-looking-trend sweep. Net read of the week:
we are at an **information ceiling, not a model ceiling** — even orthogonal external
data (building permits/violations) is flat at the granularity the public data allows.

## Chat agent (agentic AI)

The agent went from a rough stub to a responsible, evaluated, single-runtime system.
Deepak owns the workstream; most of these are hardening PRs.

### Responsible-AI framing + guardrails (#55) — and follow-ups (#66)

- One source of truth for the prompt (`run_local.py` now reads the same
  `system_prompt.txt` as the deployed agent).
- The prompt presents a **predicted risk signal, never a verdict**: never says a
  place is "safe"/"unsafe", never tells the user whether to eat somewhere, never
  declares one place definitively safer than another. Reframes "is X safe?" into
  signal + drivers + caveat. No medical/legal advice.
- A **SCOPE** section keeps it to Chicago food-safety risk and resists prompt-injection.
- **Anti-fabrication:** when a venue has no match it reports **no number** instead of
  estimating one; the prediction-vs-verdict caveat goes in **every** response (the
  runtime is stateless); low **temperature 0.2**.
- A platform **Bedrock Guardrail** (`create_guardrail.py`) adds denied topics.
- #66 corrected over-claims in the comments: the contextual-grounding filter is *not*
  active as wired, so anti-fabrication rests on the system prompt + tool grounding,
  not the platform grounding filter.

### Tool correctness (#56, #57, #58, #66)

- **#56** — `explain_restaurant` was miscounting inspection outcomes: "Out of
  Business", "No Entry", "Not Ready", "Business Not Located" (~44k events) all fell
  into the `else` branch and were reported as **passes**. Now classified explicitly
  with an `other` bucket, and history is sorted newest-first inside the handler.
  Also: on an Overpass outage `find_restaurants` now returns a top-level `{"error"}`
  object instead of a fake restaurant that crashed `get_safety_score`.
- **#57** — `get_safety_score` matched the city record on **street address alone**,
  which is wrong where many establishments share an address (O'Hare has 264 at one
  address) and silently dropped all-but-one record per address. Now matches on
  **address *and* name**, keeps every record, and returns *no match* rather than a
  confident wrong one.
- **#58** — locks in the **no-record** rule (decision record 0010): a matched venue
  returns the published batch score directly (no model call); an unmatched venue
  returns `risk_score: null` / `status: "no_inspection_record"`. The model is never
  called at request time. This removed the earlier cold-start feature-builder path.
- **#66** — restores single-occupancy match recall that #57 regressed, scopes the
  lat/long path to the Chicago bounding box, and makes the result classifier null-safe.

### Third-party reviews (#63 tool, #65 eval, #70 wiring)

- **#63** adds an opt-in `find_reviews` tool that returns **attributed deep links**
  (Yelp / Google Maps / web) on food-safety topics — cleanliness, pests, food
  quality, illness. It never scrapes (their Terms of Service forbid it), needs no
  API key, makes no network call, and stores nothing. Reviews are **not a model
  feature** and can never change a score — every response carries a disclaimer.
- **#70** wires it into the deployed AgentCore path (#63 only registered it locally)
  and tunes the links to be real and topic-scoped (validated against a real
  restaurant).
- **#65** adds eval cases locking in the boundary: reviews never become a verdict and
  never move a score.

### Eval harness (#60) — and architecture docs (#59)

- **#60** adds `agents/eval/run_eval.py`: a gated, two-layer eval. The **deterministic**
  layer runs first (free, no Bedrock) — a self-test of the guardrail checker and a
  **faithfulness** sweep that asserts `get_safety_score` relays `scores.json` values
  exactly. Only if those pass does the **guardrail** layer run six adversarial
  categories, graded by an **Amazon Nova Pro** LLM judge. First live run: faithfulness
  **25/25**, guardrails **5/6** — and it caught a real bug (a bare "No" on a no-record
  venue reads as a safety verdict), fixed in #55. Ships an `eval-agent` repo skill.
- **#59** documents the agent architecture and each tool's input/output contract in
  `agents/README.md` (the agent-internal shapes are not part of the cross-team parquet
  contract).

### Single canonical runtime + isolation + memory (#80, #72/#74, #75)

- **#80** — there were **two diverged agents**, and the deployed one was the *wrong*
  one (3 tools, no `find_reviews`, and it tried **SageMaker inference at request
  time**, violating the batch-score contract). This repoints the AgentCore runtime at
  the contract-correct `agents/entrypoint.py` and deletes the ~4,400-line duplicate.
- **#72 → #74** — the deployed agent reused **one module-level `Agent`**, so on a warm
  container conversation history leaked across callers. Now a fresh `Agent` is built
  per request. (#72 got stranded onto an already-merged branch; #74 re-lands it.)
- **#75** — adds multi-turn memory by **replaying the conversation through the caller**
  (no server state), treating the client history as untrusted input (text-only turns,
  capped, forced into Bedrock's strict alternation). Tools re-run each turn, so a
  client-supplied prior score is never treated as ground truth.

## Web app

### New features

- **Inspection comments (#51)** — each inspection in the detail timeline now expands
  on click to show the full violation comments (one per line), with accessible
  toggles and WCAG-AA contrast. Comments are sharded by license (256 files, ~255 MB,
  gitignored) and live on S3.
- **Show-more inspections (#49)** — the "Show N older inspections" button actually
  works now (it was a dead button); a "Show fewer" control collapses it back.
- **Real per-inspection trend chart (#62)** — the detail-page chart now plots the last
  ~5 scored inspections at their **real dates** with a y-axis and a hover tooltip,
  consuming the forward-looking `trend_slope`. The line/dots are a **neutral colour** —
  the single coloured direction signal is the header arrow/label, so the drawn line
  can't disagree with it. No "city median" line (it would compare a Model-1 median
  against Model-2 dots). The how-it-works page explains "prediction as of each
  inspection date" and the latest-inspection anchoring.
- **Site-wide floating chat launcher (#83)** — a button in the bottom-right of every
  page opens a compact corner panel that reuses the full `ChatInterface`; an expand
  control routes to `/chat`. Hidden on `/chat` itself. No new dependencies.
- **Client-side search restored (#54)** — a slim search index (~1.1 MB gzipped) lets
  `/?q=`, `?tier=`, and `?sort=` work again in the browser after #46 dropped
  server-side `searchParams` to unblock the static export.

### Fixes & polish

- **Empty location fields (#71)** — the detail header rendered orphaned `· ·` separators
  and a blank pill because `neighborhood`, `zip`, and `facility_type` ship empty for
  **every** establishment today. Now the location line is built from only the present
  parts and the pill is gated on a value.
- **Map popup z-index (#77)** — a pin popup near the top of the map rendered *behind*
  the floating search bar; one CSS rule raises it above.
- **Type scale (#81, #85)** — the app had **no shared type tokens** (~29 inline sizes,
  many 0.5px apart). Introduced a 12-rung `@theme` scale and swept all 23 files onto
  it; 0 arbitrary text sizes remain. The search input stays ≥16px so iOS doesn't zoom
  on focus. #85 removed a dead `--text-base--line-height` var (Tailwind v4 reserves the
  `base` keyword) and documented the quirk.

### Web-app data source (#41, #42, #46, #43, Jun/Deepak)

- **#41** — the app reads `scores.json` + history from S3 (`@aws-sdk/client-s3`) with a
  mock fallback for clean clones.
- **#46** — unblocked the CloudFront static export: the home page dropped server-side

- **#43** (Deepak) — the original agentic chat UI (`/chat`), the Lambda proxy that signs

## Infrastructure, AWS & deploy

### S3 storage seam (#64, re-landing #40)

One local-or-S3 IO seam (`foodsafety/io/storage.py`) routes every parquet / JSON /
joblib read+write through a single resolver — local path by default, or an `s3://…`
base via `FOODSAFETY_DATA_DIR`. **No new dependencies** (pyarrow's native S3
filesystem). Ingest, feature build, both retrains, and the history export all run
identically on a laptop or against S3. Adds `scripts/publish.py` + `make publish` (a
model-agnostic, versioned-model publish to S3) and a standalone `ingest_raw.py`; the
features path becomes versioned (`processed/features/<name>.parquet`).

> **#40 was stranded** — it was reported merged but landed on an already-merged branch
> 11 minutes too late, so nothing reached `main`. **#64 re-lands the exact #40 head
> rebased onto current `main`** and supersedes it.

### Web deploy moved to CloudFront/S3 (#67) and comment fix (#78)

- **#67** — a `deploy-web.yml` GitHub Actions workflow builds the static export and
  publishes to the CloudFront-fronted S3 site on every push to `main`, **restoring
  "merge to `main` = publish"**. Amplify had been stuck on a stale build since Jun 22
  (it's provisioned for SSR but `main` switched to a static export). Uses OIDC (a role,
  no long-lived keys).
- **#78** — inspection comments were blank in production: the static export bakes data
  at **build time**, but the workflow ran `next build` **before** configuring AWS
  creds, and the comment shards have no committed fallback. Fix: creds-before-build,
  re-shard the 256 md5 shards into per-license files at prebuild (keeps worker memory
  flat), and pin the data bucket to `us-east-1`.

### Agent auto-deploy (#82)

A `deploy-agent.yml` workflow auto-deploys the AgentCore agent on merge to `main`
(mirroring the web deploy), and `scripts/deploy_aws.sh` was hardened for unattended
runs: fail (not warn) on missing S3 data, retry the runtime-ARN lookup, pin proxy
deps, re-apply the Lambda role policy every run, and a gated post-deploy smoke test.
